# ADR-0010 — Student app: TLS pinning, key custody and credential hardening

- **Status:** Accepted (S12, 2026-10-26)
- **Context:** The student app ships as a PWA (every phone) and as an ICTU-signed Android APK (NFC tap). Both talk to the
  LabPass API over HTTPS on a publicly trusted certificate (Q13). The phone credential must not be copyable.
- **Decisions:**
  1. **No certificate pinning.** The API uses a public CA certificate that ICTU IT renews (often automatically, e.g.
     Let's Encrypt). Pinning would brick installed APKs on every rotation, and it is impossible for the PWA. Instead:
     HTTPS only, HSTS at the proxy, short-lived access tokens, rotating refresh tokens with family revocation, and every
     credential operation bound to a server challenge.
  2. **Device key (Android):** non-exportable P-256 key in the Android Keystore, StrongBox when available, with
     `setUnlockedDeviceRequired(true)`; the HCE service answers only when the phone is unlocked
     (`requireDeviceUnlock="true"`). The attestation chain is sent at enrollment and stored for audit only.
  3. **Passkey (web):** user verification required; backup flags (BE/BS) are recorded by the server at enrollment.
  4. **Response QRs** (offline fallback) are bound to one kiosk challenge and expire after 60 s; on Android the screen
     cannot be captured while one is shown, and brightness is raised for the kiosk webcam.
  5. **APK signing key custody:** the release keystore is generated by ICTU IT, stored offline in the ICTU safe with a
     second encrypted copy held by the IT director; developers never hold it (RSK-17). See
     [`docs/runbooks/android-release.md`](../runbooks/android-release.md).
- **Consequences:** a compromised CA could intercept traffic, but could not forge a tap or scan (signatures are
  bound to server nonces and verified against keys registered at enrollment). Losing the signing key forces a
  re-install for every Android user, hence the two-person custody.
